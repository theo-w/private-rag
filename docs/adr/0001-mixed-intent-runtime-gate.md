# mixed 意图的双侧取证用运行时门控强制，而不是只靠提示词

mixed 问题（文档侧 + SQL 侧都要证据）上，模型会在一侧零证据时提前宣布可以作答；提示词硬规则（修法 A）能把复发率压低（c03 SQL 回查 20%→100%）但只是概率性的，同一规则还曾被一次无关提交顺手删掉而无人察觉。我们决定再加一层运行时门控（修法 C）：mixed 意图下任一侧证据为零时拒绝 final，强制调用缺失的工具，可用环境变量整体关闭。

## Considered Options

- 只靠提示词（修法 A）：读数好看但会复发，且规则在 git 里脆弱。
- 只加双侧读数（修法 B）：能测量缺口，不能消除缺口。
- 运行时门控（修法 C）：确定性消除缺口，代价是被拦时多一次工具调用（单条耗时上升），且强制检索可能查到无关证据。

## Consequences

门控拦截以独立的轨迹步骤类型记录并计入每条样本的拦截次数，评估报告有「至少被拦一次」的占比读数；耗时上升是门控的正常代价，不是缺陷。提示词与评估口径保持与 v7 系列可比。
