# MCP 工具面只有两个只读工具，不暴露运行时 SQL 与入库

v7 的 agentic 链路里有三个工具：`kb_search`、只读 `sql_query`、以及运行时查询的护栏。把这套能力暴露给外部 MCP 客户端时，我们决定只给两个：`kb_search`（只检索，返回编号证据与引用元数据）与 `ask`（检索 + 作答，返回带 `[n]` 的回答），并明确不给 `sql_query`、不给入库/写库、不给会话历史。

理由是护栏的设计前提变了：`sql_query` 的只读限制（单条 `SELECT`、表白名单、强制 `LIMIT`）是按「调用方是本机这一个进程、授权来自 `sources.yaml`」设计的，它防的是模型写错 SQL，不是防一个不受控的调用方。MCP 客户端可以是任意外部程序，把同一能力交出去等于把业务库开放给任意拿到这个进程的人——只读不代表无害，表结构与全表内容本身就是敏感信息。入库方向同理：写库会改演示库与词法索引，一个外部客户端不该有这个能力。

## Considered Options

- 三个工具全暴露（含 `sql_query`）：外部客户端能做跨侧推理，功能最全；但把「本机 + 配置授权」这个前提丢掉了。
- 只暴露 `kb_search`：最保守，但外部客户端拿不到成句回答，`ask` 的价值（复用同一条生成链路与引用口径）就没了。
- 只暴露 `kb_search` + `ask`（选定）：外部客户端读到的是「已入库的内容」——`source_type=sql` 能选到的只是入库时的行级文档，不是当场查业务库。

## Consequences

- MCP 面与 agentic 面不等价：外部客户端问不出「库里现在有多少件」这类实时数值，只能问已入库的内容。这是边界，不是缺陷。
- 工具定义里显式声明 `readOnlyHint: true` / `destructiveHint: false`，客户端据此知道这两个工具不会改动任何东西。
- `ask` 单轮、不带 history：多轮追问由客户端自己组织上下文。要支持多轮，得先解决「谁持有会话」这件事，与 v3 的内存会话是另一件事。
- 想在 MCP 上查业务库，前提是先给这个进程建立独立的授权与鉴权，再谈暴露。
