# v7.4 诊断：模型把对话历史当成事实来源，还原指代后不回查工具

> **代码与数据位置**：本文引用的代码、`eval/v7_agent_qa.jsonl` 的三条 `coreference` 样本与
> `eval/reports/v7_3_coreference_report.*` 都已在 `main` 上（v7.3 经 PR #12 并入，merge 提交 `4ee6564`）。
> 本分支 `v7.4-history-as-evidence` 基于该 `main`，只多本文这一个提交，文中行号可在当前检出直接打开。
> 本文只做诊断，不改任何行为。

## 结论

路由和指代消解都没坏：c03 判的是 `mixed`，「刚才那条记录」也被正确还原成香蕉（回答里自己写了「香蕉」）。
缺的是第三条约束——**指代还原以后，那一半还得重新取证**，而这条约束在链路上压根不存在：步进决策的充分性判据没排除历史，
最终作答的接地规则没标注历史，评估口径又只考一侧，所以这个缺口既不会被拦住，也不会被看见。

三个层次，按可控程度从难到易：

1. **步进决策**：`sufficient` 完全由模型自报，代码不校验；判据措辞让「历史里已有的事实」也算被支撑。
2. **最终作答**：`FINAL_PROMPT` 把历史渲染成无编号、无标注的裸文本，紧贴证据块，实际地位等同于一条匿名证据。
3. **评估口径**：`expected_source` 只能标一侧，双侧样本「查了几侧」没有任何指标量得到。

## 一、缺口在步进决策，不在路由

c03 的实测读数（`eval/reports/v7_3_coreference_report.json`，config=`agent`）：

| 读数 | 值 |
|---|---|
| `intent` | `mixed` |
| `tool_calls` | 1（只有 `kb_search`） |
| `tool_steps` | 3 = 路由 1 + 工具 1 + 宣布作答 1 |
| `stop_reason` | `final` |
| 引用来源 | `docs/beginner-guide.md` / `README.md` / `docs/ROADMAP.md`（全是文档侧） |
| 证据块含 `2026-01-15` | 0 / 3 块 |

最后一行是关键：那一半时间戳**不在任何证据块里**，只可能来自对话历史，回答里也明写了「（对话历史中已给出）」。
`tool_steps=3` 说明第二步 `planner.decide()` 直接选了 `final`，SQL 侧从未被尝试。

为什么它认为证据已充分，两点都能从代码读出来：

- `runtime.py:398`（`run_stream` 对应 `:660`）把 `decision.sufficient` 原样赋给本地变量，没有任何「`mixed` 是否两侧都拿到过证据」的检查；
  `prompts.py` 的 `_sufficiency()` 在字段缺失时一律按「足够」处理。也就是说，只要模型说够，链路就信。
- `STEP_PROMPT` 第 1 条把 `sufficient` 定义成「现有证据能否支撑问题要的那项事实」，但同一个 prompt 里，
  「问题要的那项事实」（2026-01-15）已经明明白白写在历史段落里。第 1 条从没说「支撑」只能看上面那个
  「已收集的证据」段落，v7.3 新加的第 9 条还进一步把历史抬成解指代的正常依据。
  模型判 `sufficient=true` 在它自己的读法下是自洽的，这不是随机失误。

对照证据：`intent=mixed` 的 7 条里有 5 条（m01–m05）都是 `tool_calls=2`、两侧证据齐全，它们全都不带历史。
**没有历史可抄时，`mixed` 是老实查两次的。**

## 二、最终作答这一处，agentic 比固定链路更松

实测 `FINAL_PROMPT` 在 c03 场景下的渲染结果（v7.3 版模板 + 真实历史）：

```text
5. 相关句子后用 [编号] 标注依据……
6. 「没有对话历史」不是拒答理由：指代本系统自身的提问按证据作答……
用户: 香蕉现在多少钱？
助手: 香蕉当前单价 6.5 元，记录更新时间是 2026-01-15。

证据：
[1] (来源: docs/beginner-guide.md)
```

历史直接裸贴在规则块与证据块之间，**没有小标题、没有编号、没有「这不是事实来源」的标注**，
看起来就像规则的第 7 款或者一条匿名证据。而固定链路的 `generation.py:97` 反而写了完整措辞：
「对话历史（仅用于理解当前问题的指代，不能作为事实依据）」。
`FINAL_PROMPT` 第 1 条「证据之外的事实一句都不要写」字面上覆盖这种情况，但被这样渲染出来，实际约束不住。

`agent/tools.py` 的 `render_evidence()` 只给工具产出的块编号，历史永远不进引用列表，
所以抄历史得到的那半句在引用列表里没有对应条目——用户看不见它的出处。

## 三、波及面：评估集 1/3，但生产面比这大，而且是静默的

- **带历史的样本只有 3 条**（c01/c02/c03），抄历史 1 条。样本层面看是 1/3。
- **c02 是反例**：它的历史里同样写着「橙子当前单价 12.5 元，记录更新时间是 2026-01-10」，模型照样去跑了
  `sql_query`，检索五项全 1.000。所以触发条件不是「有历史」，而是
  **问题含多个子问题 ∧ 其中一子问题的答案已在历史里 ∧ 那一半属于另一个工具**。单侧指代问题不会触发。
- **`mixed` 判对但只查一侧的，全量 29 条里只有 c03 一条**（另一条 `tool_calls=1` 的 mixed 是 d02，它本身是单侧问题，SQL 一次就够）。
- **生产暴露面更大**：`api/routes.py` 四个问答端点（`:238`、`:295`、`:398`、`:473`）都把
  `session.history_for_prompt()` 原样传进去，默认最多 6 轮 / 3000 字符 / 单条 800 字符（`config.py:82-84`），
  历史里的 assistant 内容就是上一轮的完整回答。连着追问同一条记录的不同字段是常见用法，
  上一轮刚报过的价格、库存、更新时间天然躺在 prompt 里。
- **而且是静默的**：c03 的 `source_hit`、`citation_rate`、`citation_validity` 全是 1.000，`answer_rate` 计入已回答，
  `intent=mixed` 看着正常。原因是 `evaluation.py:513-517`——`expected_source` 是单个字符串，
  判定用 `any(...)`，双侧样本只能要求「任一侧命中即算过」。c03 标的是文档侧，SQL 那一半没有任何指标覆盖。
  v7.3 自己在 `eval/README.md` 的读数限制里写了这条：「混合样本的 `expected_source` 只标一侧……
  它的 `evidence_hit@3` 1.000 不等于两半都查过」，但当时只记为口径限制，没修。

## 四、修法选项与代价

| 选项 | 做法 | 会动的文件 | 代价 |
|---|---|---|---|
| **A 提示词**（弱保障） | `STEP_PROMPT` 第 1 条限定「只有『已收集的证据』算支撑，对话历史不算」，并加一条「已判定需要两侧、某一侧还没有证据时不得选 `final`」；`FINAL_PROMPT` 给 `{history_section}` 套上固定链路那句「不能作为事实依据」的标题段，并明确历史里的事实要写进回答必须先查 | `private_rag/agent/prompts.py`、`tests/test_agent_planner.py`（扩 `TestCoreferenceResolution`） | 与 v7.3 第 9 条方向相反（那条催「别停」，这条要「别抄」），同一个本机 27b 可能反向过度检索：单侧问题（c02/d02）多跑一次 SQL，耗时在 v7.3 同子集 89.1 秒的基础上再涨；保障仍是软的 |
| **B 评估口径**（先让缺口可测） | `expected_source` 支持多值，`source_hit` 改成「声明的每个来源都必须被引用」；另加一个不调模型的逐条读数（按引用是否含 `#sql_query` 判「两侧是否都有证据」），把 c03 与 mixed 5 条改标双侧 | `private_rag/evaluation.py`（`EvalSample`/`load_dataset` 校验/`score_deterministic`/`_result_to_dict`/`build_report`/`render_markdown`）、`eval/v7_agent_qa.jsonl`、`eval/README.md`、`tests/test_evaluation.py`、重跑 29 条报告 | 与历史报告口径不可比，要重跑一条基线（v7.2 那轮 26 条 1348.6 秒、v7.3 同子集单条 89.1 秒，全量重跑按 25–45 分钟估）；`tests/test_evaluation.py` 里 `expected_source` 断言密集，改动面不小 |
| **C 运行时硬约束**（强保障） | 代码级两侧覆盖检查：`intent=mixed`、步数未用尽、某一侧零证据时不许进 `final`——把缺口写进 `missing` 让现有 `missing_rule` 哨兵生效，或直接补一次该侧工具；带开关（仿 `RAG_DISABLE_AGENT_NONE_PROBE`） | `private_rag/agent/runtime.py`（`run` 与 `run_stream` 两处）、`tests/test_agent_loop.py`、`config.py` | d02 这类「判 `mixed` 但单侧就够」会被强推一次无效 SQL；两条链路各写一遍容易漂移；把行为约束从提示词搬进代码，模型换得快、规则改得慢 |
| **D 接受「历史即证据」** | 明确写进口径：允许直接引用上一轮结论 | `FINAL_PROMPT` 显式放行、`agent/tools.py` 的 `render_evidence` 给历史编一个可引用条目、README 与 ROADMAP 口径 | 不推荐。SQL 是运行时直连，价格/库存/更新时间本来就会变，历史可能就是错的；那一半要进引用列表就得给历史造出处，与 v2 起「每个事实带引用溯源」的产品主张正面冲突；这类样本怎么算分还得再定一套规则 |

**建议顺序：B 先行，A 紧跟，C 作为 A 不奏效时的兜底。**
理由很直接：v7.3 就是先例——三处提示词硬规则写完，靠逐条人读回答才发现这个新缺口。
没有 B，A 改完只能再靠人读一轮报告来验收，改没改对说不出数字。

## 五、取证入口

评估跑的时候设了 `RAG_DISABLE_AGENT_TRACE=1`，`trace_id` 不能逐条回放，所以**步进决策当时的 `reason` 没有任何留档**。
上面第一节的机制解释来自代码与提示词的渲染结果，不是从轨迹里读到的模型原话——这条区别要一并带走。
想拿到模型自己说的理由，可以只跑 c03 一条并把 trace 打开：评估用的 `configure_eval_env()` 走的是 `os.environ.setdefault`（注释里就写着「已有值优先，便于临时覆盖」），外部显式给值即可覆盖掉关闭开关：

```bash
RAG_DISABLE_AGENT_TRACE=0 python3 scripts/evaluate.py --dataset eval/v7_agent_qa.jsonl --configs agent --agent-sources config/sources.eval.agent.yaml --skip-ragas --ids c03 --output eval/reports/diag_c03.md --json-output eval/reports/diag_c03.json
```

落盘后看 `steps` 里 `kind=final` 那一步的 `reason`，就是模型宣布证据已足够时给的理由（`runtime.py` 把步进决策的
`reason` 写成这一步的 `final_reason`）。

另外记一笔与本次同源的风险：`_sufficiency()` 在模型漏写 `sufficient` 字段时默认按「足够」处理
（为了兼容被截断的 JSON 与老格式），这会让抄历史更容易过关——但它同时是 v7.2 有意为之的兼容行为，
动它等于换一条口径，不属于本问题的修法。

## 六、状态（2026-11-20，`v7.4-two-sided-source`）

**第三层成因（评估口径）已按 B 处理：缺口现在量得到。** 落地形态与本文第二节的 B 略有出入，
两点都是刻意的：

- **没有改 `source_hit`。** B 原写的是把 `source_hit` 改成「声明的每个来源都必须被引用」，
  那样 v7 / v7.2 / v7.3 三轮报告的既有数字就不可比了。实际做法是加新可选字段
  `expected_sources` + 新读数 `both_sides_hit`（声明的每一侧都要在全量引用里出现才判 1），
  旧指标定义一字未动，逐条仍可比。
- **没有按 `#sql_query` 片段判侧。** 改为按声明的来源标签匹配（沿用 `_source_matches`），
  这样文档侧也能成为声明的一侧，而不是只能判「有没有 SQL 证据」。
- 新读数扫全量引用、不套 `@3` 窗口；只统计声明了双侧的 6 条（m01–m05 + c03）。

按新口径回算 v7.3 那一轮的既有引用数据：`both_sides_hit` = **5/6 = 0.833**，判 0 的正是 c03
（只引 `docs/beginner-guide.md`/`README.md`/`docs/ROADMAP.md`，1 次 `kb_search`，没回查 SQL）——
同一条在那轮的 `source_hit` 与 `evidence_hit@3` 都是 1.000。这就是「缺口此前不可见」的直接证据。

**第一、二层成因未动**：`runtime.py` 仍采信模型自报的 `sufficient`，`FINAL_PROMPT` 仍把
`{history_section}` 无标注地渲染在规则段与证据段之间。修法 A（提示词）与 C（运行时硬门禁）
仍是未勾项，c03 「把历史当事实来源」这条行为本 PR 不改。

**本 PR 的 29 条实跑**（`eval/reports/v7_4_two_sided_report.md`）：`both_sides_hit` = **6/6 = 1.000**，
c03 这轮真的回查了 SQL（`tool_calls=2`，SQL 引用排在第 4 位）。与上一轮同样数据回算出的 5/6 = 0.833 对照，
结论是「抄历史不回查」属**间歇行为**：它不是每轮都触发，但第一、二层成因没动、也没有硬门禁，
随时可以再出现——区别只在于现在再出现会被判 0，并单独进报告的「失败与关注案例」。
另一点实测：c03 与 m04 的 SQL 引用这轮都落在引用列表第 4 位，若新读数沿用 `source_hit` 的前 3 条窗口，
两条都会被误判成「只取到一侧」，这就是新读数扫全量引用的理由。
